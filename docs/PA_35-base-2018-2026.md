## 1. Problem

The user added a batch for 2018–2026 so the stored base covers every F&O underlying in every year, not only today's 31
survivors after 2018. Rules: same quality checks as batch a; reconcile with the live store for the 31 shared symbols
(any unexplained mismatch is a FAIL; the live store is not overwritten); lots verified only where the file states
them; the 2025+ rows built but only counted; the 2021-03-30 hole kept; stop if rows or disk exceed the estimate by more
than 25%. Also: match batch a's large moves to corporate actions, and find what drives the parity flags.

bytes per row for every year: an estimating error. Per-year rates are in the [data catalog](data_catalog.md).

### Reconciliation with the live store (31 shared symbols, 2018–2026)

First run: rows identical in every year and both tables (0 only-live, 0 only-base); two value differences.

| Difference | Rows | Explanation |
|---|---|---|
| `known_from` on 2021-03-26 | 31 summary, 7,696 chain | **Expected.** The base counts the 2021-03-30 archive hole as the session it was, so 03-26 data is public on 03-30; the live store skips it (03-31). The reconciliation now counts exactly this case as explained |
| `lot_size`, 2022 | 13 summary rows (DIVISLAB 2022-06, WIPRO 2022-11/12) | **A defect in the base, fixed.** Around a lot change the open-interest method gives alternating values (200, 100, 200…). One despiking pass can flip them the wrong way; the live store converges because every nightly build despikes again. Repeating the base's despiking until stable matches the live store exactly (measured: 5 or more passes, 0 mismatches) |

Fix: `despike_until_stable` in the builder, applied to the stored base of both batches with `restabilize` (snapshots
first). 877 lot values changed, all derived and UNVERIFIED (2015: 449, 2016: 128, 2017: 62, 2018: 54, 2019: 48,
2020: 61, 2022: 65, 2023: 10). Trial-log event 4 (`data_correction`).

**Second run: PASS.** Every year 2018–2026, both tables: 0 rows only in one store, 0 values differing, apart from the
explained `known_from` on 2021-03-26. For 2025–2026 this compared keys and equality only; no statistic was computed.
